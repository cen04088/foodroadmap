# 프론트엔드 (Next.js) — 설계 문서

- 작성일: 2026-09-03
- 상태: 승인됨 (구현 계획 수립 대기)
- 상위 스펙: [2026-09-01-route-restaurant-service-design.md](2026-09-01-route-restaurant-service-design.md) §2.6, §3, §5

## 1. 범위

상위 스펙 §2.6의 MVP 기능 범위를 구현하는 Next.js 웹 프론트엔드.

- 출발지/도착지 입력(주소·장소명 검색) → 경로 검색 → 경로상 맛집 리스트(거리/시간순) + 지도 표시
- 방송프로그램 필터, 업종 필터
- 반경 조정 UI, 회원/즐겨찾기/공유 기능은 상위 스펙 §8에 따라 이번 범위 밖

백엔드(`GET /api/route-restaurants`)는 이미 구현·배포 준비 완료 상태이며, 이 문서는 그 API를 소비하는 프론트엔드만 다룬다. 단, CORS 미들웨어가 백엔드에 없어 이번 작업에 백엔드 쪽 CORS 추가가 포함된다 (§5).

## 2. 기술 스택 및 아키텍처

- **Next.js (App Router)**, 단일 페이지(`app/page.tsx`), 클라이언트 컴포넌트 중심
- **Tailwind CSS** 스타일링
- 별도 상태관리 라이브러리 없음 — React `useState`/`useReducer`로 충분한 범위 (폼 상태 + 검색결과 하나)
- **클라이언트가 백엔드를 직접 호출**하는 구조 (Next.js 라우트 핸들러로 프록시하지 않음) — 인증 없는 공개 조회 API라 프록시로 얻는 이득이 적고, 홉이 하나뿐이라 가장 단순함. 나중에 인증/캐싱이 필요해지면 프록시 레이어를 추가할 수 있음
- 환경변수:
  - `NEXT_PUBLIC_KAKAO_JS_KEY` — 카카오맵 JS SDK 앱 키 (Kakao Developers에 이미 등록되어 있음, REST API 키와는 별개)
  - `NEXT_PUBLIC_API_BASE_URL` — 백엔드 주소 (로컬 개발: `http://localhost:8000`)

### 디렉토리 구조

```
frontend/
  app/
    page.tsx              # 메인(유일한) 페이지
    layout.tsx
  components/
    SearchForm.tsx         # 출발/도착 입력 + 장소 자동완성 + 검색 버튼
    FilterBar.tsx           # 방송프로그램 드롭다운 + 업종 자유입력
    MapView.tsx              # 카카오맵, 경로선, 맛집 마커
    RestaurantList.tsx        # 결과 리스트 (시간순 정렬)

    kakaoPlaces.ts                # 카카오 Places 검색 래퍼

```

## 3. 화면 구성 — 단일 페이지

메인 화면 하나에 다음이 모두 표시된다 (별도 결과 페이지로 분리하지 않음):

- 상단: `SearchForm` (출발/도착 입력) + `FilterBar` (방송/업종 필터)
- 검색 실행 전: 지도만 표시(기본 위치), 리스트 영역은 안내 문구
- 검색 실행 후: 지도에 경로선 + 맛집 마커, 리스트에 시간순 카드들이 나란히 표시 (데스크톱: 좌우 분할, 모바일: 상하 배치 — 반응형)
- 리스트 항목에 마우스를 올리면 지도에서 해당 마커가 하이라이트된다

## 4. 컴포넌트

### 4.1 SearchForm

- 출발/도착 각각 텍스트 입력 필드
- 입력 시 카카오맵 JS SDK의 `kakao.maps.services.Places`로 장소 검색 → 자동완성 드롭다운 표시
- 드롭다운에서 장소를 선택하면 해당 장소의 `lat`/`lng`를 내부 상태에 저장하고, 입력창에는 장소명이 남는다 (좌표는 사용자에게 보이지 않음)
- 두 위치 모두 선택되어야 "검색" 버튼이 활성화됨
- 반경(`radius_km`) 조정 UI는 포함하지 않는다 (상위 스펙 §8, MVP 범위 밖). 백엔드는 이미 `radius_km` 쿼리 파라미터를 지원하므로, 나중에 UI만 추가하면 됨

### 4.2 FilterBar

- **방송프로그램**: 드롭다운 선택. 상위 스펙 §2.2에 나열된 14개 프로그램(슬러그+한글명)을 프론트엔드에 고정 목록으로 넣는다. 드롭다운 값 표시는 한글명("또간집")으로 하고, `broadcast` 쿼리 파라미터에도 그 **한글명**을 그대로 보낸다 — 백엔드 `broadcast` 필터는 슬러그·표시명 둘 다 매칭하도록 이미 구현되어 있고(상위 스펙 §5의 예시 `broadcast=또간집`과 일치), 응답의 `restaurants[].broadcasts`도 표시명 배열이라 왕복이 자연스럽다. "전체"(필터 없음) 옵션 포함. 새 방송이 추가되면 이 목록을 수동으로 갱신해야 한다는 걸 감안한 선택 — 지금은 백엔드에 방송 목록 조회 엔드포인트가 없고, 이 정도 빈도로 바뀌는 값이라 API를 새로 만들 필요는 없다고 판단
- **업종**: 자유 텍스트 입력. 업종 값이 크롤링 데이터에 따라 다양해서 고정 드롭다운으로 다루기 어려움. 백엔드의 `category` 파라미터는 정확히 일치하는 값만 필터링하므로(대소문자/공백 무관 매칭 없음), 이 제약을 입력창 placeholder에 안내(예: "한식, 일식 등")

### 4.3 MapView

- 카카오맵 JS SDK로 지도를 렌더링
- 검색 결과의 `route.points`를 이어 폴리라인으로 경로 표시
- `restaurants` 배열의 각 항목을 마커로 표시, 마커 클릭 시 인포윈도우(상호명/거리/시간/전화/영업시간)
- SearchForm에서 장소를 선택하면(검색 실행 전이라도) 지도 중심을 해당 위치로 이동

### 4.4 RestaurantList / RestaurantCard

- `restaurants` 배열은 백엔드가 이미 누적시간순으로 정렬해 반환하므로 그대로 렌더링
- 카드에 표시: 상호명, 업종, 경로로부터의 거리(km), 출발 후 누적시간(시:분으로 변환), 방송프로그램 목록, 전화번호, 영업시간
- 카드 hover/클릭 시 지도의 해당 마커를 하이라이트(인포윈도우 열기 또는 마커 스타일 변경)

## 5. 백엔드 변경 — CORS

`backend/app/api/main.py`에 `fastapi.middleware.cors.CORSMiddleware`를 추가해 프론트엔드 개발 서버(`http://localhost:3000` 등, 환경변수로 오리진 목록을 받도록)에서의 요청을 허용한다. 이 항목은 지난 최종 리뷰에서 남겨둔 이슈이기도 하다.

## 6. 데이터 흐름

1. 사용자가 출발/도착을 검색해 선택 → lat/lng 확보 (§4.1)
2. "검색" 클릭 → `GET {API_BASE_URL}/api/route-restaurants?origin={lat},{lng}&destination={lat},{lng}&broadcast={선택값?}&category={입력값?}` 호출
3. 응답의 `route.points`로 지도에 경로선, `restaurants`로 마커+리스트 렌더링
4. 필터(방송/업종)를 바꾸면 같은 origin/destination으로 **다시 요청**한다 (카카오 Directions API도 다시 호출됨 — 매 필터 변경마다 경로 재계산 비용이 들지만, MVP에서는 단순함을 우선한다. 트래픽이 늘면 "필터 없는 결과를 한 번만 받아 클라이언트에서 재필터링"으로 최적화 가능 — 지금은 YAGNI로 하지 않음)
5. 요청 중에는 로딩 상태 표시, 완료되면 지도/리스트 갱신

## 7. 에러 처리

| 상황 | 처리 |
|---|---|
| 장소 검색 결과 없음 | "검색 결과가 없어요" 안내 (자동완성 드롭다운 내) |
| 백엔드 500 (카카오 키 누락 등 서버 설정 오류) | "일시적인 오류입니다, 잠시 후 다시 시도해주세요" — 내부 사정(에러 메시지 원문)은 노출하지 않음 |
| 백엔드 502 (카카오 경로 API 실패) | "경로를 가져오지 못했습니다, 다시 시도해주세요" |
| 매칭된 맛집 0건 (`restaurants: []`) | 에러 아님 — "이 경로 근처엔 방송 맛집이 없어요" 빈 상태 안내 |
| 백엔드 자체 연결 실패 (네트워크 오류) | "서버에 연결할 수 없습니다" |

## 8. 테스트 전략

- 순수 로직(카카오 API 응답 파싱, 시간 포맷 변환, 필터 쿼리 조합 등)은 최소한의 단위 테스트로 검증
- 나머지(폼 입력, 지도 렌더링, 검색 흐름 전체)는 개발 서버를 띄워 실제 브라우저에서 골든 패스를 직접 확인하는 것을 주요 검증 수단으로 삼는다 — 지도/자동완성처럼 실제 카카오 SDK와 얽힌 부분은 자동화 테스트보다 육안 확인이 더 신뢰도 높은 검증
